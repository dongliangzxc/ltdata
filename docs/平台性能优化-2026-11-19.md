# 平台性能优化：第一轮（2026-11-19）

更新（2026-11-20）：用户明确要求移除已有 URL 映射的冲突硬拦截，现按人工所选型号覆盖映射；详见 [批量确认映射覆盖说明](批量确认映射覆盖-2026-11-20.md)。以下为第一轮性能优化时的规则和验证记录。

已按用户确认的顺序完成本地优化：批量确认、请求主循环阻塞、发布批量入库。没有提交、部署或操作生产数据库；本轮不需要数据库迁移。

## 改动与验证结果

| 功能 | 修改前 | 修改后 |
|---|---|---|
| 批量确认 500 条 | 5,501 次 SQL 调用、501 次提交 | **38 次 SQL 调用、6 次提交**（含原有后处理） |
| 同品类元数据预览 10,000 行 | 10,001 次品类查询 | **2 次品类查询**（解析 1 次、权限检查 1 次） |
| 发布 1,005 条，每条一个规格 | 主数据逐行 upsert，规格逐个创建 ORM 对象 | **2 次主表批量写入 + 2 次规格批量写入**，分析库统一提交 1 次 |
| Excel 解析、文件复制和鉴权 | 异步请求中直接执行同步工作 | 同步导入路由由 FastAPI 线程池执行；鉴权会话从创建到关闭在同一个工作线程内执行 |

SQL 调用数为本地隔离 SQLite 的 `before_cursor_execute` 次数，不能等同于生产 MySQL 的精确物理语句数或线上耗时。发布调用次数由新增完整入库测试验证；MySQL 主表 upsert 分支另有 SQL 编译检查。没有进行真实 MySQL 并发或性能测试。

## 批量确认保留的行为

- 每批最多 100 条，锁定并重读匹配记录及原始数据，使用数据库连接查询当前 URL 映射，保留数据库实际的键比较规则。
- 保留状态变化、未识别品牌、无效目标型号、URL 冲突及逐条失败提示；保留人工确认前的状态快照，已有扩展值和候选不清空。
- URL 相同的输入合并写入，后面的有效输入覆盖 URL/价格等值；请求中重复的匹配 ID 仍只确认第一次，后续记录反馈“状态已变更”。
- 正常批次统一更新、删除旧属性和写回 URL 映射；异常批次先回滚，再拆分重试，直到隔离坏行。已提交的前批成功结果不会被后批错误回滚。
- 属性匹配与价格审核仍只接收成功确认的 ID，保持现有后处理行为。

主要实现：`backend/app/services/batch_review_confirm.py`、`backend/app/api/match_api.py`。

## 请求阻塞与元数据处理

型号、URL 映射、元数据、品牌别名、属性规则和历史库的同步 Excel 入口统一由线程池执行，内部文件保存也改为同步函数，避免名为异步的函数在事件循环里直接复制大文件。鉴权完整数据库会话通过 `run_in_threadpool` 执行，不把同一个会话拆成多个并发工作。

元数据品类解析使用单次请求内缓存，沿用原有大小写、名称、前缀和未知品类处理；导入每批最多 300 行 upsert，保留重复输入最后一行生效及原有返回计数。一个文件的多个写入批次仍在同一事务内，失败由请求会话关闭回滚。

新增 HTTP 并发测试用可控制的等待模拟慢解析/慢鉴权，验证处理尚未结束时，其他请求和 `/health` 仍能返回。真实 Excel 解析仍有 CPU/GIL 成本，线程池也有容量限制，不能保证任意并发量下无等待。

## 发布处理

主数据、规格、属性查询、已发布 ID 回查及旧规格删除的批次上限均为 1,000；规格使用字典批量插入，不逐个创建需要回取主键的 ORM 对象。分批写入不分批提交，保持分析库整次发布的事务边界。

保留原有同键覆盖字段、重复发布、条目属性覆盖型号规格、销量系数、跳过 pending/停用条目等规则。跨批次重复商品只写一套规格；后续批次出错后回滚可恢复之前的完整发布结果。

发布入口仍同步等待，发布查询仍会一次载入本任务结果；后台化及读取内存峰值优化未纳入本轮。原有处理库与分析库分开提交的行为保持不变。

主要实现：`backend/app/services/publisher.py`。
