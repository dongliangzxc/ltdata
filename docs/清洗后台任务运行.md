# 清洗后台任务

创建品类任务、月度创建/追加/重新清洗时，快照与 `clean_task_runs` 队列在同一事务提交，接口返回 `match_status=queued`。后台从持久化快照执行；关闭浏览器、刷新页面、单独重启 API 均不取消任务。

## 运行与发布

生产使用 `docker-compose.rds.yml` 的 `backend`、`clean-worker`、`frontend` 三个服务。`clean-worker` 与 API 使用同一后端镜像，命令为 `python -m app.workers.clean_worker`，等待 API 健康后启动。API 入口先执行迁移，失败即退出，不会在缺少字段时继续启动。

从当前生产 p74 升级时需执行 p75（任务进度兼容字段）和 p76（持久化队列表及队列索引）。发布前保留后端、前端旧镜像，确认没有正在执行的重任务；构建后同时更新三个服务。发布后检查迁移版本、三项容器状态、真实队列消费、轻量进度接口及失败重试。

开发环境的 `docker-compose.yml` 同样包含独立 worker。更新既有开发数据库时先执行 `alembic upgrade head`。直接启动本地 API 时，需额外启动 `python -m app.workers.clean_worker`；未启动 worker 的任务会保留在队列中，待 worker 启动后执行。

`CLEAN_BACKGROUND_ENABLED` 默认开启。关闭开关仅用于兼容原同步入口或测试；切换为同步模式前必须停止 worker 并确认没有执行中的任务，不应同时运行两种模式。

## 普通月度追加（p77）

新建任务、显式重新清洗、强制重建和归档任务重建仍执行全量。已成功完成任务的普通月度追加只处理本次新快照；无新增时返回 `match_status=unchanged`，不入队。已有人工、属性或发布记录的追加限制维持现状，未放开。

p77 在 `clean_task_runs` 中增加 `mode`、`snapshot_start_id`、`snapshot_end_id`、`input_count`。API 先锁住原任务，再保存新增快照和执行范围，统一提交。范围使用当前任务内新增快照的最小/最大编号和预期条数；快照编号按插入先后递增，其他任务在此区间的编号被任务条件排除。worker 验证范围及原始行数量，不允许读不到时退回整单。原始快照和范围在失败、进程重启后仍保留。

增量读取旧结果的去重键，以原保留行为优先；清洗、型号匹配、候选、属性和价格审核仅写本批结果，匹配上下文整批复用。整个增量的产物、累计数量和队列完成状态在一个事务提交；阶段进度仍独立写入。失败或提交前进程被强杀时回滚本次全部产物，原结果保留；重试沿用原来的执行方式和快照范围，不清空整单。累计 `row_in` 包含已入快照但本批尚未处理完成的记录，`row_out` / `row_filtered` 仅计成功提交的结果。

普通追加不顺带刷新旧数据。请求改变原任务清洗配置会被拒绝，应选择明确的重新清洗；规则或映射库更新后，若需要旧数据也采用新规则，同样需要显式重洗。兼容开关 `CLEAN_BACKGROUND_ENABLED=false` 仍走旧同步整单流程，生产增量仅在后台模式启用。

页面区分本批输入数量、当前阶段已处理/总数及任务累计结果；列表和轻量进度的更新时间统一按北京时间返回，避免旧格式差异使前端忽略进度。发布需同时更新 API、worker、前端并执行 p77；p76 既有队列行默认保留 `full` 模式。

回滚到不支持增量的版本时必须停止 worker，并停止追加与重试入口；不能让旧 worker 把增量任务按全量执行。保留 p77 字段和队列，等待恢复支持增量的 worker。存在未完成（含失败可重试）的增量任务时，p77 降级会拒绝删除执行范围。

## 执行、进度和恢复

MySQL 数据库级 `GET_LOCK` 让不同 worker 容器、旧的同步重任务入口和旧型号匹配线程共用一个执行名额。worker 在持有锁的连接上执行，连接中断使执行失败，锁由数据库释放。SQLite 开发环境用文件锁；生产使用 MySQL。

队列表每个清洗任务只有一行，按排队时间、编号顺序领取；重试排在队尾。领取后保存执行 token，进度和失败写入检查 token，防止旧执行覆盖后续尝试。只允许一个重任务执行，但数据库可持久保存其他待执行任务，不为每个排队任务创建线程。

实际进度存于队列表的阶段、已处理条数、总条数中，涵盖清洗、型号匹配、属性匹配和价格审核。进度写入限频为每秒最多一次，阶段切换和阶段完成立即写入。MySQL 使用独立连接，仅更新队列进度行，避开清洗产物外键在任务主表上持有的锁，也不为显示进度提交清洗产物。SQLite 有数据库级写锁，进度随执行事务的自然提交可见。兼容的 `clean_jobs.progress` 仅代表原有阶段值，页面不将其展示为精确的总体百分比。

页面有进行中任务时每 3 秒调用 `/api/clean/jobs/progress?ids=...`，每次最多 200 个任务，只查询状态和队列进度，不统计匹配结果。隐藏页面时暂停轮询，结束后刷新一次完整统计。返回结果按品类权限过滤。月度队列缓存会核对任务状态，识别独立 worker 的完成状态。

worker 拿到执行锁后，仅把队列中遗留的 `running` 任务标记为“已中断”，不改动其他旧任务或未开始的 `queued` 任务。执行中断不会自动断点续跑；失败任务保留快照、已有部分产物和错误信息，可从原快照重试。重试会从头清理、重建该任务产物；人工处理（包括人工扩展字段）或已发布的任务不允许直接重试。价格审核失败会让后台任务失败，避免审核未完成却显示成功。

排队/执行中任务不能追加、重洗、删除、发布或修改人工结果。重试和修改入口在写入前校验状态、取得任务行锁，并重新建立读取事务，避免等待人工修改提交后仍沿用旧读取快照。旧的补充数据和保留人工结果的规则重跑入口维持原同步事务语义，但与后台 worker 共用重任务互斥锁。

## 回滚

先停止接收新任务，等待正在执行的任务结束，再停止 `clean-worker`；若强制终止，恢复新版本 worker 时会标记中断。恢复旧 API 和前端镜像时保留 p75/p76 及队列表，避免丢失排队任务。旧版无法消费新队列，待恢复新版 worker 后继续执行。不要在仍有 worker 运行时切回不支持队列的旧 API，也不要自动回退数据库结构。
