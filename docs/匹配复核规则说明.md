# 匹配复核规则说明

本文档梳理「型号匹配」页面中确认匹配、未识别品牌、待确认、待确认 URL、争议、排除等状态的当前规则。规则依据当前代码实现整理，主要来源：`backend/app/services/matcher.py`、`backend/app/api/match_api.py`、`frontend/src/pages/Match/index.tsx`。

## 1. 自动匹配总体流程

匹配引擎对每条清洗后的商品数据采用瀑布式降级流程：前一阶段命中后停止，不再进入后续阶段。

| 阶段 | 匹配方式 | 命中后的状态 / 来源 | 说明 |
|---|---|---|---|
| S0 | URL 精确匹配 | `url_matched` / `s0` | 从宝贝链接提取平台与商品 ID，查人工维护的 URL 到型号映射。置信度最高。 |
| S0.2 | 历史库匹配 | `matched` / `historical` | 同样按平台与商品 ID 查历史映射。 |
| S0.5 | 显式规则匹配 | `matched` / `s0.5` | 按规则优先级，对商品名做精确或包含匹配。 |
| S1 | 原品牌字段缩窄候选 | `matched` 或 `text_only` / `s1` | 用原品牌字段对应到品牌后，在该品牌下找型号。 |
| S2 | 标题品牌码匹配 | `matched` 或 `text_only` / `s2` | 原品牌未识别时，从商品标题中识别品牌码，再在该品牌下找型号。 |
| S3 | 标题品牌名匹配 | `matched` 或 `text_only` / `s3` | 品牌码未命中时，用品牌名继续识别。 |
| S4 | 型号码全局兜底 | `matched` 或 `text_only` / `s4` | 不限制品牌，全局找型号；通常需要更谨慎复核。 |

S1-S4 如果文本匹配找到了型号，但商品存在可解析 URL 且 URL 未命中 S0 映射，则状态记为 `text_only`，表示「待确认 URL」；如果没有这种 URL 风险，则状态记为 `matched`。

## 2. 状态定义

| 状态 | 页面含义 | 产生方式 | 是否可发布 / 进入后续 |
|---|---|---|---|
| `url_matched` | URL 映射命中 | S0 自动命中 URL 映射 | 是，计入可发布。 |
| `matched` | 已自动匹配 | S0.2、S0.5、S1-S4 自动命中，且无需 URL 复核 | 是，计入可发布。 |
| `text_only` | 待确认 URL | 文本匹配命中型号，但 URL 存在且未命中 URL 映射 | 需要人工复核后更稳妥；同标题批量确认可处理。 |
| `pending` | 待确认 / 未匹配 | 自动匹配未找到最终型号 | 否，需要人工确认、排除或继续补数据。 |
| `confirmed` | 确认匹配 | 人工选择型号并确认 | 是，计入可发布；来源记为 `manual`。 |
| `excluded` | 已排除 | 人工判定该条不应入库或不参与匹配 | 否。 |
| `disputed` | 争议暂存 | 人工暂存争议并填写原因 | 否，保留在复核队列，可再次确认或排除。 |

## 3. 未识别品牌规则

`brand_identified` 是独立于 `match_status` 的品牌识别标记，用于区分「系统已经拿到稳定品牌识别依据」和「系统尚未拿到稳定品牌识别依据」。注意：页面仍可能展示原品牌或入库品牌，例如原始数据里有“康佳（KONKA）”，但如果匹配流程没有把它转化为可确认型号的稳定依据，仍可能进入「未识别品牌」队列。

当前规则：

| 场景 | `brand_identified` | 说明 |
|---|---:|---|
| S0 URL 映射命中 | 1 | URL 映射已直接关联到型号。 |
| S0.2 历史库匹配 | 1 | 历史映射命中时标记品牌已识别。 |
| S0.5 显式规则匹配 | 1 | 规则命中指定型号时标记品牌已识别。 |
| S1 原品牌字段识别到品牌 | 1 | 即使最后没有找到型号，也会进入「待确认」而不是「未识别品牌」。 |
| S2/S3 标题中识别到品牌码或品牌名 | 1 | 同上。 |
| S4 仅靠型号全局兜底或品牌识别依据不足 | 0 | 如果系统没有稳定品牌识别依据，前端归入「未识别品牌」队列；这不等于页面完全没有品牌文本。 |

前端「未识别品牌」队列本质是 `brand_identified = 0` 的待复核数据。批量确认前也会校验：如果条目 `brand_identified === 0`，会提示「未识别品牌，请先补充品牌写法」，不允许直接批量确认。

## 4. 页面队列和筛选口径

匹配页当前复核队列包括：

| 页面 Tab | 后端查询口径 | 业务含义 |
|---|---|---|
| 未识别品牌 | `brand_identified = 0` 的复核数据 | 系统品牌识别依据不足或未形成可确认型号；页面可能仍显示原品牌/入库品牌，需先补品牌写法或单条确认型号。 |
| 待确认 URL | `match_status = text_only` | 文本已命中型号，但 URL 没有映射，需要人工确认 URL 与型号是否一致。 |
| 待确认 | `match_status = pending` | 自动匹配未能确认型号；若 `brand_identified = 1`，通常表示品牌已识别但型号未定。 |
| 争议暂存 | `match_status = disputed` | 人工暂时无法定论，保留原因后回队列。 |
| 已自动匹配 | `match_status IN (matched, url_matched)` | 自动可发布结果；前端合并展示 URL 命中和其他自动命中。 |
| 已确认 | `match_status = confirmed` | 人工确认后的结果。 |
| 已排除 | `match_status = excluded` | 人工排除结果。 |
| 干扰项过滤 | 清洗阶段过滤结果 | 非匹配状态，用于查看被清洗过滤的数据。 |

补充说明：`filtered` 和 `disabled` 不是 `match_status`。`filtered` 来自清洗或干扰项过滤结果；`disabled` 来自匹配结果的禁用标记 `is_disabled`。它们会出现在页面统计或队列中，但不属于 `url_matched/matched/text_only/pending/confirmed/excluded/disputed` 这套匹配状态。

搜索字段支持商品名称、原品牌、入库品牌。类目筛选依赖调度批次中的类目关联；如果同一原始数据在同批次有多条调度记录，接口会去重，避免复核列表重复。

## 5. 人工操作规则

### 5.1 确认匹配

人工确认某条数据为指定型号时：

- `model_id` 更新为人工选择的型号。
- `match_status` 更新为 `confirmed`。
- `matched_by` 更新为 `manual`。
- `match_source` 更新为 `manual`。
- 清空争议原因和复核备注。
- 写入 `reviewed_at`。
- 若原始数据带有可解析 URL，会同步维护 URL 到型号映射，后续相同 URL 可走 S0 命中。

### 5.2 排除

人工排除时：

- `match_status` 更新为 `excluded`。
- `model_id` 置空。
- `matched_by` 更新为 `manual`。
- 排除原因写入 `review_note`。
- 写入 `reviewed_at`。

### 5.3 争议暂存

暂存争议时必须填写原因：

- `match_status` 更新为 `disputed`。
- `matched_by` 更新为 `manual`。
- 原因同时写入 `dispute_reason` 和 `review_note`。
- 写入 `reviewed_at`。

### 5.4 撤销

人工三态 `confirmed`、`excluded`、`disputed` 支持撤销。撤销依赖操作前保存的快照字段，尽量恢复到原状态、原型号、原匹配来源；如果历史数据没有快照，则兜底恢复为 `pending`。

## 6. 批量确认规则

### 6.1 普通批量确认

普通批量确认用于把勾选条目或当前筛选结果按首候选型号批量确认为 `confirmed`。

当前普通批量确认只允许处理：

- `pending`
- `text_only`

普通批量确认还会校验首候选是否有效。未识别品牌、没有候选型号、品牌码或型号码为空、品牌码或型号码为 `-` / `--` 的条目都会失败，不会被确认。

### 6.2 同标题批量确认

同标题批量确认用于把同一规范化标题下的多条数据确认到同一个型号。

当前同标题批量确认可处理的状态包括：

- `pending`
- `text_only`
- `disputed`

以下状态不会被同标题批量确认覆盖：

- `matched`
- `url_matched`
- `confirmed`
- `excluded`

同标题匹配会对标题做规范化：大小写折叠、全半角归一、去掉空格和常见标点，再比较是否相同。这个规则适合处理同一商品标题在不同来源行中的重复复核，但不适合跨标题扩散。

## 7. 候选型号规则

匹配过程中会保留候选型号，接口返回时按 `rank` 展示。候选去重规则是：同一 `model_id` 只保留最高分，最终取前 5 个候选。

批量确认取首候选时，按 `rank` 最小优先；如果同一 `rank` 有多条记录，则按候选记录 ID 升序取第一条。若第一候选没有有效 `model_id`，该条视为没有可用首候选，不会回退到同 rank 的其他候选。

## 8. 可发布和属性补全口径

匹配页统计中的可发布数当前按以下状态计算：

- `url_matched`
- `matched`
- `confirmed`

「未补属性」列表的口径是：状态在 `matched`、`confirmed`、`url_matched` 中，且没有属性匹配结果。也就是说，自动匹配和人工确认都可能进入属性补全；`pending`、`text_only`、`disputed`、`excluded` 不进入该列表。

## 9. 待业务确认问题

| # | 问题 | 当前默认假设 |
|---|---|---|
| 1 | `text_only` 是否必须人工确认后才能发布，还是允许直接进入发布？ | 当前统计口径没有把 `text_only` 计入可发布；默认需要人工确认。 |
| 2 | `matched` 自动匹配是否需要抽检比例或置信度阈值后再发布？ | 当前代码只按状态放行，没有额外抽检规则；默认自动匹配可发布。 |
| 3 | `brand_identified = 0` 是否一律禁止批量确认？ | 当前前端禁止未识别品牌直接批量确认；默认先维护品牌写法或单条处理。 |
| 4 | `disputed` 是否允许被同标题批量确认覆盖？ | 当前代码允许；默认同标题确认可解决争议项。 |
| 5 | `excluded` 是否需要结构化排除原因枚举？ | 当前为文本备注；默认暂不强制枚举。 |
| 6 | S4 全局型号码兜底命中后是否应强制复核？ | 当前无 URL 风险时会进入 `matched`；默认可发布，但建议需求方确认是否要单独进入待确认。 |
| 7 | `filtered` / `disabled` 是否需要在页面上与匹配状态分组视觉隔离？ | 当前会出现在同一复核页统计或队列中；默认在文案上说明它们不是 `match_status`。 |
| 8 | 单条确认是否允许从任意状态改为 `confirmed` / `excluded` / `disputed`？ | 当前单条接口比普通批量更宽松；默认允许人工单条纠错，但建议业务确认边界。 |
