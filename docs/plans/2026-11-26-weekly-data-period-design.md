# 上传、分发、清洗支持周度：现状与方案

日期：2026-11-26。状态：早期方案存档；新版方案已于2026-11-27实现并上线，见下方链接。

2026-11-27更新：已基于本轮讨论整合为 [新版完整方案](./2026-11-27-weekly-data-period-proposal.md)，后续评审以新版为准；本文保留现状代码依据和早期分析。

## 1. 需求理解与结论

本方案将“时间细分到周度”理解为**数据所属的业务周期**，即原来的月报数据扩展为月报、周报两种粒度；上传时间、分发执行时间、清洗执行时间仍是操作时间，不用于推算业务周。

当前不是完全没有周字段，而是周字段只在部分存储和历史匹配环节存在，上传、任务范围、去重和发布尚未贯通。因此不能仅增加页面“周”筛选。

建议保留月度处理能力，增加独立的周度处理能力；同一周期可以追加，不同周分别建任务；月汇总与周明细在任务和业务统计中明确隔离。

本次梳理依据本地代码与已有需求记录，未连接生产数据库。现网字段实际分布、旧数据中有效周值的数量、累计值/区间值占比尚未核验。

## 2. 当前链路

## 3. 先明确周期口径

用户已明确：采用月内第几周，以用户上传为准；周次限定为1、2、3、4、5，接受数字或对应数字字符串。周次作为用户提供的业务周期标签，平台不自行规定日期边界。具体上传交互及其他业务规则仍为建议：

1. **周按用户上传的月内序号表示。** 展示为“2026年11月第3周”，每月重新编号。文件已有周列时逐行读取；同一文件可含多个周。建议为没有周列的单周文件提供上传时指定周次的方式；两处均填写且冲突时，展示冲突供用户修正。
2. **年月与月内周共同确定周期。** 用户提供202611和第3周，就按该标签入库、分发、清洗；平台只做格式归一化和必要校验，不推算第3周是哪几天，不强制按1—7日等日期段划分，不根据上传日期确定业务周。跨月报表的归属月份也以用户提供的业务月份为准，不自动拆分总量。同一业务范围内需保持周次标注口径一致，才能汇总比较。
3. **显式区分月度与周度。** 月度记录没有周；周度记录必须有可确定的周期。选择周报后周为空、格式歧义或文件与列值冲突，应提示修正，不能静默降为月报。
4. **确认指标是否为本周区间值。** 如果是“截至本周的本月累计销量/销额”，各周不能直接相加；累计快照应先确定取期末值或差分规则，不默认当作区间周报。
5. **建议允许月报和周报分别留存，统计显式选粒度。** 对同一来源、品类、平台、月份的重叠数据提示，但不直接沿用旧草案的“一律禁止共存”。月报与周报不能直接相加；是否需要禁止混传仍待确认。

若采用区间周报，月汇总的销量、销售额可以对归属于该月且完整覆盖的周记录求和；均价按有效销售额/销量计算，缺少真实销额或销量为零时不能自动补造。跨月归属和缺周应标明，不能自动认定周汇总等于完整自然月。

## 4. 建议的数据设计

### 4.1 统一周期身份

保留现有 `month` 和 `week`，新增明确的 `period_type`（month/week）及规范化、非空的 `period_key`。由统一函数负责解析、校验、标签和查重身份，避免上传、补充数据、清洗、发布分别拼接。

周期键示意：

- 月度：`M:202611`。
- 月内周度：`W:202611:03`，表示用户提供的2026年11月第3周，不隐含具体日期范围。

周序号可采用独立整数 `week_of_month`，既有 `week` 字段保留来源值，避免把历史年内周号误认为月内周。新上传的周次按下述已明确的输入规范处理；历史年周值不能直接按月内周解析。

### 4.2 周次输入规范（已明确）

**适用范围：** Excel/CSV周列、上传时手动指定的周次及接口周次参数统一使用本规范。周次表示用户定义的月内序号，不隐含日期范围。

| 项目 | 明确规则 |
|---|---|
| 取值范围 | 仅1、2、3、4、5，分别表示当月第1至第5周；不接受第6周或年内周号 |
| 数字输入 | 接受数值1、2、3、4、5；值必须为整数，不四舍五入、不截断。Excel读取出的数值3.0与数值3等价，接受并归一化为整数3 |
| 字符串输入 | 去除首尾空白后，只接受单个半角字符 `"1"`、`"2"`、`"3"`、`"4"`、`"5"`；例如 `" 3 "` 接受并归一化为整数3 |
| 不接受的写法 | `"第3周"`、`"周3"`、`"W03"`、`"03"`、`"3.0"`、`"三"`、`"３"`、`"3周"`、`"1,2"` 等均不符合输入格式 |
| 不接受的类型或数值 | 0、6、负数、非整数（如2.5）、布尔值、数组、对象等均无效；不能将true当成1 |
| 空值 | 已明确为月度时，周字段可缺省、为null、空字符串或纯空白；已明确为周度时，这些情况均提示缺少周次，不能按月度入库。字符串 `"null"` 不视为空值 |
| 月份关联 | 周次必须与业务月份共同使用。例如202611+3表示2026年11月第3周；202612+3是另一个周期 |
| 月份天数 | 各月份统一允许1～5；不根据2月、30天或31天月份自动推算周数，不擅自拒绝用户提供的第5周 |
| 归一化 | 合法数字与合法字符串统一保存/传递为整数1～5，同一月份的3与 `"3"` 属于同一周期，参与同一套去重和任务范围计算 |
| 页面展示 | 输入提示为“请填写1～5的整数，如3（表示本月第3周）”；只读展示可写“第3周”或“2026年11月第3周”，展示文案不是可接受的上传值 |
| 非法值提示 | 明确给出行号、字段、原值和原因，例如“第18行：周次‘第3周’格式不正确，请填写1～5的整数或对应数字字符串”。周次有误时先修正再进入对应周周期，不静默置空或改值 |

示例：数值3、文本 `"3"`、文本 `" 3 "` 归一化后均为3；数值3.0也为3，但文本 `"3.0"` 不接受。此规范替代此前接受“第3周”“W03”的宽松写法建议；本轮仅更新方案，尚未实现校验。

不建议仅将可空 `week` 塞入唯一索引：月度空周需要稳定身份。新周期键还需配套现有其他可空维度的处理，保留缺商品ID记录的既有语义，不顺带改变所有旧数据去重规则。

### 4.3 各阶段保持同一周期

| 位置 | 建议变化 |
|---|---|
| 原始数据 | 去重身份中的月份扩展为规范周期；保持国家、平台、商品ID维度，同周重传去重、不同周共存 |
| 清洗结果 | 保存周期；清洗去重键由商品ID+月份+店铺名扩展为商品ID+周期+店铺名；缺ID时仍仅识别同一原始记录 |
| 清洗任务 | 任务范围从品类+平台+月份扩展为品类+平台+周期；结构化保存周期类型/键并建查询索引，`source_scope` 保留来源快照信息 |
| 发布数据 | 增加周及周期字段；平台+商品ID+月份的发布身份扩展为平台+商品ID+周期；upsert、去重计数、规格ID回查同步更新 |
| 上传文件 | 从实际入库行生成周期类型、周期范围摘要；一个文件可包含多周，文件级摘要不代替行级周期 |

首期不扩展多周合并任务。一个文件包含多个周时，分发完成后生成多条周期队列，由分析师分别或批量创建各周任务。

## 5. 页面与接口方案

### 上传

- 列映射增加“周”，兼容 `week/周/周度/周次`；自动模板、手动映射、旧上传入口、异步确认和补充上传统一写入周期。
- 上述兼容指列名别名；列内值只接受1～5的数字或对应数字字符串，详见4.2，不接受“第3周”等文本。上传模板示例使用1、2、3、4、5。
- 上传确认展示粒度和识别出的周期；月报保持原操作习惯，周报要求能确定周。
- 以用户提供的业务年月和月内周为准；周列支持逐行映射，无周列的单周文件建议支持上传时统一指定。显式输入与文件内容冲突时先修正，不静默覆盖。
- 文件名识别周号作为辅助信息，仅接受约定格式；与列值冲突时列出冲突供修正，避免沿用“文件名月份覆盖全文件”后误写多周或跨月文件。
- 原有数据质量“提示后仍然上传”不因此整体收紧。不能确定周期身份的周报属于新增的周期范围问题，建议修正后再正式入库，需确认这一规则。
- 原始数据列表、筛选选项、预览和导出同步展示周期，便于核对。

### 分发

- 复用按文件/上传批次逐行执行的品类规则，不额外按周重复跑同一文件，不引入时间规则配置系统。
- 分发结果查询、下载、规则命中核对增加“粒度+周期”条件，周选项来自实际数据。
- 规则核对按周期+品类+平台+规则展示，保留零命中规则；导出任务保存当次完整条件，下载和重试沿用原条件。
- 周度导出必须可识别具体周：无模板导出已有周列可复用；模板导出在必要时补周期列，同时保留原字段及来源追溯。
- 最新已完成分发批次的选择逻辑保持一致，周维度只用于过滤和聚合，不用于选择“最新批次”。

### 清洗

- 筛选增加“粒度（月度/周度）”，按选中粒度显示月份或具体周；队列、任务列表、任务名都展示周期。
- 同品类+平台+同周期创建或追加；其他周新建任务。原月度任务只接月报记录，不能吞入整月周明细。
- 创建、追加、重洗、强制重建、归档恢复、检查补齐都使用精确周期范围；同时更新并发锁、缓存键、页面行键和跳转参数。
- 补充上传继承目标任务完整周期；文件显式给出的周期与任务不符时提示，不静默覆盖。补充只处理新增快照范围，保留已有人工处理和发布结果。
- 批量建任务仍是一条周期队列对应一个任务。重建或清理一个周任务，不能影响其他周和月度任务。
- 转移到其他任务的选择器展示周期；跨周期转移需校验，避免原始行周期与目标任务范围不一致。

### 接口兼容

建议新增通用周期入口，例如 `GET /clean/pool`、`POST /clean/tasks/upsert-period`，使用 `period_type + period_key`；旧 `/pool/monthly`、`/tasks/upsert-monthly` 保留为明确的月度适配入口。

分发、原始数据和导出查询增加可选粒度/周期条件，继续接受原 `month/months`。旧调用仍保留月份过滤含义；月报专用入口明确只取月度，跨粒度列表则返回周期字段。对面向业务指标的旧分析接口，建议默认保持月报口径、显式切换周报，避免新周数据悄悄改变原月度结果。

“兼容旧参数”不等于“未传周就把月报周报混合统计”，各类接口需在实现前列清默认取数契约并回归。

## 6. 下游边界

推荐本期包含发布保周和业务统计的粒度隔离，否则前三个环节完成后仍会在发布时覆盖不同周数据，或使现有统计重复计算。

- **必须贯通**：发布存储与唯一身份、结果导出保周、历史匹配周值一致、分析取数隔离月报/周报。
- **处理进度**：可以在总览继续展示工作量总数，但周期明细要分开；行数、任务数是处理工作量，不能解释为去重商品数或市场销量。
- **周汇总到月**：只在区间值及归属规则明确后提供，不能把原月报再叠加一次。
- **历史匹配**：新月内周与历史年内周不能仅凭相同字符串认定同周期。只有能确认周次口径一致或存在明确对应关系时才做同周匹配；历史 `W21`、`周36` 等记录不能直接重编号。新月内周标签本身不提供日期，平台不据此自动换算历史年周。保留同月无周回退能力。
- **价格审核**：首期保留前6个月时间窗口；读取历史时隔离报表粒度，避免周报重复增加样本权重。是否需要“最近N周”审核窗口另行确定。
- 完整周度趋势图、环比同比和多周合并任务可作为后续范围，不是前三个业务环节支持周度的必要条件。

## 7. 数据迁移与落地顺序

1. 按用户提供的业务年月和月内周建立周期契约，明确周列映射、单周文件手动指定及冲突处理；确认月周共存及指标口径，不再要求平台定义每周日期边界。
2. 只读盘点原始/清洗/历史/发布数据的有效周值、空字符串、非法值、重复键及任务覆盖关系。不能将所有旧记录的周一律清空；无周且月份有效的存量才能直接映射为月度。原来上传时已按月跳过的周记录，需要有原件才能重新核对恢复。
3. 增量增加字段和索引，分批回填规范周期；处理无法确定周期、混合周期旧任务及潜在重复项后，再切换唯一约束。保留原ID、人工确认、发布关系和原始周值备查。
4. 贯通上传→分发→清洗→补充/补齐→导出→发布；API与后台worker一并兼容新旧字段。旧分析库数据没有周，只有能从来源行和匹配结果可靠追溯时才回填，不能按发布时间猜周。
5. 完成回归和迁移演练后，再开放周度入口。评估大表建索引及回填影响，验证现有按月覆盖索引和分发池查询性能，避免周聚合引发全表扫描。
6. 回退时先停止周度写入并保留新字段、原始行及结果；已有周数据时不能直接降回旧月度唯一约束，也不能让旧发布程序继续处理周任务。正式回退流程需随最终迁移脚本验证。

## 8. 验收条件

1. 同国家、平台、商品、同月不同周的两行均可入库并建成独立任务；同周在同文件、跨分块、跨文件重传均按既有重复策略处理。
2. 月报旧模板、文件名识别、异步上传及旧月度接口继续可用；周报缺周、非法序号、输入冲突均明确提示；用户上传的业务月份和周次跨页面一致，不根据上传日期或月份天数擅自重编号；一份多周文件按行归属不同周期。
3. 月报与周报共存时，任务范围无交叉，统计不相加重复；累计快照不能误作可相加的区间值。
4. 同周新增数据只追加到该周任务；重洗、重建、补齐、补充上传及跨任务转移不能串周；已有人工和发布结果按原规则保护。
5. 重新分发仅使用最新已完成来源版本；查询、规则命中核对、导出和清洗队列的周期计数可对账。
6. 不同周发布后各自保留，重复发布同周更新本周，规格关联准确；撤销一个周任务发布不影响其他周。
7. 相同口径的月内周优先、同月回退通过；历史年内周不能误命中月内周，明确周期映射单独验证；月度价格审核不被新增周样本悄然改变。
8. 迁移保留原始ID及人工结果；混合周期旧任务有处理清单；真实MySQL唯一约束、并发请求、缓存隔离及查询性能通过验证。
9. 数字1～5及对应字符串均可用且归一化一致，首尾空白按规则处理；同月份数字3和字符串 `"3"` 去重及任务身份一致。非法写法、0/6/负数/小数/布尔值及周度空值均有明确提示；区分数值3.0与文本 `"3.0"`，全部上传入口遵守同一规范。

## 9. 需要需求方确认

- 周次来源采用何种交互？建议有周列按行读取，无周列的单周文件允许上传时统一指定；已明确以用户提供的月内周为准，无需再确认平台固定日期段。
- 销量和销额是本周区间值，还是截至本周的累计值？
- 同范围月报和周报是否允许分别保存？建议允许、任务分开、业务统计选择粒度；周数据是否继续走发布流程？建议完整保留周后发布。

周次取值及输入格式已按用户要求明确；上传交互和其他业务口径仍可继续评审，本轮保持方案阶段，尚未实施迁移。
