# 数据上传、分发、清洗支持周度：新版方案

日期：2026-11-27。状态：已实现并上线，功能版本`0908154`，迁移`p82a1b2c3d4e5`。

验收入口、测试文件与操作步骤见 [周度功能测试文档](../周度功能测试文档-2026-11-27.md)。

实现说明：业务输入仍只接受1～5。数据库使用非空`week_of_month`（内部0表示月度、1～5表示月内周）与月份共同参与索引和唯一约束，避免空周破坏月度去重；任务来源范围同时保存可读`period_key`，原始行与发布行不重复存储字符串周期键。导出月报的周次留空。存量`week`字段保留，新上传值归一化，原件保留原始输入。月报和周报分别保存、分别查询；累计指标口径尚未确认，因此不自动周转月汇总。

价格审核继续使用原月度历史窗口，新周报不会混入旧月度参考样本；历史年内周与新月内周不自动互相换算。周次文件名识别未作为本期入口，使用周列或手动指定。

本方案整合已确认的月内周次规则。第1节为已确认的业务规则；其余为据此提出的产品与技术方案，未确认的业务选择单列在第8节。

## 1. 已确认的周期和输入规则

- 周表示“某年某月的第几周”，以用户上传为准。例如202611+3表示2026年11月第3周。
- 周次只允许1、2、3、4、5，兼容数值和对应数字字符串；统一归一化为整数。
- 平台不规定第几周对应哪些日期，不根据上传时间或日历自动计算周次。各月份统一允许1～5。
- 保留原有月度处理能力。周度记录必须有月份和周次；月度记录周次为空。
- 本轮继续只出方案，不修改业务代码、数据库或部署。

### 输入约定

| 输入形式 | 示例 | 结果 |
|---|---|---|
| 整数数值 | 1、2、3、4、5 | 接受，保存为整数 |
| 数字字符串 | `"1"`、`"2"`、`"3"`、`"4"`、`"5"` | 接受，保存为对应整数 |
| 字符串首尾空白 | `" 3 "` | 去除首尾空白后接受，保存为3 |
| Excel读取的整数值浮点数 | 数值3.0 | 接受，保存为3；不截断或四舍五入其他小数 |
| 其他文本写法 | `"第3周"`、`"W03"`、`"03"`、`"3.0"`、`"三"`、`"３"` | 不接受 |
| 范围或类型不符 | 0、6、负数、2.5、布尔值、数组、对象 | 不接受 |
| 空值 | 缺省、null、空字符串、纯空白 | 月度可空；周度提示缺少周次。文本 `"null"` 不算空值 |

列名可兼容“周”“周次”“周度”“week”；列内值必须遵守上表。界面只读展示可用“第3周”，上传值仍填写3。

示例报错：`第18行：周次“第3周”格式不正确，请填写1～5的整数或对应数字字符串。`

## 2. 现状与必要改动

本地代码梳理表明，原始数据和清洗结果已有week字段，但标准上传映射、写库、去重和任务范围尚未贯通；分发执行可以复用，时间查询仍主要按月；分析库没有周字段，发布唯一身份也按月。

因此需要同时处理“正确保留周数据”和“按周组织任务”，并让导出及发布继续保留周期。只添加周筛选会留下数据被按月跳过或覆盖的问题。

代码依据和逐环节分析保留在 [前轮现状梳理](./2026-11-26-weekly-data-period-design.md)。本方案未核验生产存量数据。

## 3. 页面和流程方案

### 3.1 数据上传

建议在现有上传确认中增加“数据粒度：月度/周度”，默认月度，兼容原来的上传习惯。

| 场景 | 建议交互 |
|---|---|
| 月度文件 | 沿用现有月份识别和映射，周次为空 |
| 周度文件有周列 | 映射周字段，逐行读取；允许一份文件包含第1周、第2周等多周数据 |
| 单周文件没有周列 | 允许上传时统一指定1～5中的一个周次，作用于当前文件 |
| 文件周次与手动周次冲突 | 展示冲突，修正后再确认，不静默覆盖 |
| 月度模式出现非空的已映射周字段 | 提示改为周度或修正映射，不能直接丢弃周值 |

确认页和上传历史展示数据粒度、月份、周次摘要和写入/跳过数量；多周文件显示实际包含的周次。

周度数据的月份、周次无法确定或不符合规范时，建议阻止本次入库确认并指出具体问题。原有价格、销量等数据质量警告的“仍然上传”流程继续按原规则处理；周期校验不扩大为所有字段的强制校验。

首期周次来自周列或用户手动指定。文件名识别属于可选辅助能力，不作为本期必要依赖；不从上传日期猜周。原有文件名月份识别继续使用，月份来源有冲突时在确认页提示核对。

原始数据列表、预览、筛选和导出增加粒度、月份及周次，方便核对后续分发结果。

### 3.2 数据分发

沿用现有按文件/上传批次逐行执行品类规则的流程，分发明细继续引用原始行ID。

- 分发结果、规则命中核对增加粒度、月份、周次条件；周度下按具体周核对。
- 周次筛选可多选，仅提供1～5中的有效候选；未选择具体周时表示所选月份内的全部周度记录，不包含月报记录。
- 导出周度数据时保证有月份、周次列，保留原字段和来源追溯信息。
- 导出任务保存创建时的完整条件，重试和下载继续使用原条件。
- 仍按上传来源选择最新已完成分发批次；增加周筛选不改变来源版本的选择规则。

### 3.3 数据清洗

待入清洗队列与清洗任务按“品类+平台+业务周期”组织。业务周期包含粒度、月份，周度再包含周次。

| 数据范围 | 对应任务示例 |
|---|---|
| 耳机+京东+202611月度 | 耳机 / 京东 / 2026年11月 / 月度 |
| 耳机+京东+202611第1周 | 耳机 / 京东 / 2026年11月第1周 |
| 耳机+京东+202611第2周 | 耳机 / 京东 / 2026年11月第2周 |

- 同品类、平台、月份、同一周的数据追加到同一周期任务；不同周分别建任务。
- 月度任务只接月度数据，周度任务只接该周数据；一个多周文件可形成多条待处理队列，支持批量创建各周任务。
- 创建、追加、重洗、重建、归档恢复、检查补齐、任务转移和后台执行均检查完整周期范围。
- 补充上传继承目标任务的粒度、月份及周次；文件没有周期列时使用任务范围，有明确周期但不一致时提示修正，只清洗和匹配新增数据。
- 同一周重洗或撤销发布仅影响该周，保留其他周、月度任务及原有人工处理保护规则。
- 页面筛选、任务名称、行标识、缓存和并发控制同步区分周期。

首期建议一个任务对应一个周期，批量操作仍创建多个独立任务。

## 4. 数据身份与去重

统一增加或完善以下周期信息：

| 字段 | 用途 | 示例 |
|---|---|---|
| period_type | 月度或周度 | month / week |
| month | 业务月份 | 202611 |
| week_of_month | 规范化月内周，月度为空 | 3 |
| period_key | 非空的规范周期身份 | 月度 `M:202611`；周度 `W:202611:03` |

现有week字段保留源值或历史值，不能把历史年内周号直接解释为新月内周。周期解析及校验由统一函数处理。

| 位置 | 建议去重/唯一身份 |
|---|---|
| 上传原始数据 | 保持国家、平台、商品ID维度，将原月份维度扩展为period_key |
| 清洗结果 | 保持原商品ID、店铺维度，将原月份维度扩展为period_key；缺商品ID时保留原有按原始记录识别的规则 |
| 清洗任务 | 品类+平台+period_key；并发创建和追加时检查相同范围 |
| 发布数据 | 在原平台+商品ID身份上将月份扩展为period_key，更新对应唯一键与关联查询 |

同月份数字3和字符串 `"3"` 是同一周期；同商品同月不同周必须共存。同周重复上传继续沿用现有跳过重复的行为，不自动叠加销量或覆盖已有原始行。

避免直接把可空week加入唯一索引来识别月报；月度使用独立稳定的周期键。其他可空维度、存量重复及缺商品ID的处理在迁移中单独核验，不借本次扩展改变既有去重语义。

## 5. 导出、发布和统计

建议本期同步贯通发布保周和统计粒度隔离，保证上传到下游始终识别同一周期。

- 匹配结果导出、分发导出均保留业务月份和周次，月度的周次留空。
- 分析库保存周期；发布写入、更新、计数、规格回查及撤销发布都使用完整周期，避免第2周覆盖第1周。
- 历史同周匹配只在周期口径相同或有明确映射时启用；历史W21等年内周值不自动转换为月内周，保留现有同月无周回退能力。
- 业务指标按月报或周报分别查询；处理工作量可汇总展示，但应与商品数、销量等业务指标区分。
- 首期建议保留价格审核前6个月的时间窗口，并隔离月/周历史样本；“最近N周”的价格规则另行评审。
- 周销量、销额是否可汇总成月数据，取决于其是否为区间值、是否重复及覆盖是否完整；首期不自动生成完整月报，也不将月报与周报相加。

完整周趋势图、环比同比和多周合并任务可后续扩展。

## 6. 旧数据和接口兼容

- 旧月度模板不强制增加周列，旧月度接口保留为月报入口；新增周期接口用于周度任务。
- 查询接口继续支持现有month/months，增加粒度与周次条件。月报专用入口只取月度；周度入口不传具体周时取对应月份全部周度记录；跨粒度的原始行列表应明确标识粒度。
- 保留旧数据ID、原件、人工确认和任务关联。无周且月份有效的数据可回填为月度；已有周值、非法月份或混合周期旧任务先盘点，不统一清空或猜测周期。
- 历史发布记录只有能可靠追溯来源周期时才回填周信息。过去已被按月去重跳过的数据，需根据原件核对后才能恢复。
- 周度数据写入后，回退不能直接恢复旧月度唯一键或继续使用旧发布逻辑处理周任务；迁移演练中明确回退步骤。

## 7. 实施顺序与验收

建议实施顺序：统一周期解析与输入校验 → 盘点及迁移字段、索引和约束 → 上传及原始数据查询 → 分发查询、导出 → 周期任务及增量清洗 → 发布与下游隔离 → 回归验证。正式开放周度前完成整条链路，API与后台worker保持兼容。

关键验收：

1. 1～5的数字和对应字符串归一化一致；非法值和周度空值有行号及原因，同月份数值3和文本 `"3"` 进入同一周期。
2. 同商品同月第1周、第2周均可入库，同周在文件内、跨分块及跨文件重传按原规则去重。
3. 同一文件的多周数据分入各周队列；追加、补齐、补充、重洗、重建不串周，人工处理及其他周期结果得到保留。
4. 分发结果、清洗队列、结果导出及发布数据在相同来源与周期范围内可对账。
5. 发布不同周互不覆盖，重复发布只更新本周；撤销一个周任务不影响其他周期及规格关联。
6. 旧月度上传、任务、导出和发布回归通过；迁移保留存量关系，并验证真实MySQL约束、并发请求、缓存隔离及大表查询性能。

## 8. 仍需确认的业务选择

1. **月报、周报是否允许同范围分别保存？** 建议允许，按粒度分开处理和查询，不混合累加。
2. **周销量、销额是本周区间值还是累计值？** 在确认前不做自动周转月汇总。

周列映射、无周列时手动指定、周期错误修正后入库、发布保周均已给出具体建议，可结合本方案评审；上述建议不视为用户已授权实现。
